# SignalPay demo v3

The existing SignalPay GitHub Pages app and Android APK now start at registration/login. No new application repository, real funds, banking connection, phone OTP provider or central authentication/sync service exists.

## Registration and PIN login

Register a full name, Pakistani mobile number (03… or +923…), and an 8–12 digit PIN. Mobile ownership remains **Unverified**: there is no OTP service, no fake OTP, no SMS and no claim of verified legal identity. Registration is local to this browser/PWA or APK installation, not a globally registered phone account. Duplicate normalized mobile numbers are refused within that installation. The same phone registered independently on another installation creates a separate account; cross-device login/recovery requires a real backend and is not implemented.

Each profile gets a random ECDSA P-256 key and stable account ID derived from its public-key fingerprint. Profiles and ledger/signing-key material are encrypted with AES-256-GCM under a non-exportable key derived from the PIN using a random salt and PBKDF2-HMAC-SHA256 with 600,000 iterations. Account ID, phone lookup hash and revision are authenticated as associated data. PINs and unlocked session keys are not stored. After PIN unlock the signing key is imported as non-exportable. Full mobile number, wallet balances, history, contacts and receipt inbox are in the encrypted profile; the public local directory stores account IDs and signed public account cards (including public display names), not private wallets.

Five incorrect PIN attempts trigger a persisted cooldown, with increasing delay on subsequent groups of failures. This is a client-side demo defense: a compromised device can tamper with local attempt counters and attempt PIN guessing. Numeric PINs, frontend code and local storage are not equivalent to production bank authentication or a trusted money ledger. Do not use real/sensitive data. There is no PIN recovery. Clearing site data or uninstalling can remove accounts permanently.

Login is required again after page/browser restart. Logout clears the private UI, dialogs, QR images, draft recipients, in-memory session and keys. Other tabs for the same account are locked using a non-secret revocation marker and BroadcastChannel/storage events; another user's session is unaffected. Idle sessions lock after five minutes, and returning after over 30 seconds in the background requires PIN re-entry. Camera access stops on hide/navigation/lock. Original v2 unnamed-wallet data is preserved in its separate old database; it is not silently attributed to a newly registered user or imported as authenticated history. V3 demo accounts start at PKR 25,000.

## Personal QR and trusted recipient resolution

Receive Money shows the logged-in user's own stable signed account QR (QR protocol version 2), full account ID, Copy Account ID and Share QR. Private keys and mobile numbers are not in QR codes. Signed QR data is public, not encrypted.

A QR key signature alone does **not** establish a trusted display name. The app resolves names from a signed local registration-directory record, or an encrypted recipient record previously confirmed on this account. Unknown cross-device recipients open the amount sheet immediately with the full account ID and signed QR label filled automatically. The self-declared name is explicitly unverified. Before Review Payment, the user must independently compare the displayed name/full ID with the owner and confirm the checkbox, which saves a local contact without manual retyping. Incoming sender review likewise pre-fills read-only account details and requires an independent check. Scanned labels cannot overwrite existing registered/saved names. This is explicit local contact confirmation (trust on first use), not central/OTP/legal identity verification. Compare the ID through an independent channel; an attacker controlling that channel or device can impersonate a person.

The amount opens in a bottom-sheet style dialog, followed by Review Payment and Confirm & Send. Recipient IDs are masked in sender review and receipts. Sender and receiver history use matching transaction IDs, Sent/Received names, amount, status and date/time. All names shown in payment review come from the resolved account record, not an arbitrary QR label.

## Offline transfer and reconnect reconciliation

Delivery uses manual optical QR exchange, independent of Wi-Fi/mobile data after app preparation:

1. Receiver displays their account QR; sender scans, resolves/confirms the account record, enters PKR amount and reviews/confirms. A signed payment offer is persisted as Pending; available demo funds are reserved but recorded balance is not yet debited.
2. Receiver scans the sender's offer, resolves/confirms the sender record and explicitly accepts or rejects. Acceptance credits the receiver once and persists a signed acknowledgement; rejection records Failed without credit.
3. Sender scans the receiver's acknowledgement QR. Signature, both accounts, transaction ID, amount, currency, mode and offer hash must match. Only this verified receipt finalizes Successful/debit or Failed/release on sender. Both histories share the ID.

Receiver credit occurs before the sender gets the returned receipt. In that window sender remains Pending/reserved; this is not atomic banking settlement. Lost receipt can be reopened on receiver. No unilateral cancellation or expiry is implemented because receiver may already have accepted. Duplicate scans/imports are idempotent; conflicting IDs/decisions and wrong-account receipts fail closed. Up to 500 records are retained for replay checking; new transfers are refused at that limit.

Receiver-signed receipt bundles may be exported/imported. The per-user encrypted inbox persists imported matching acknowledgements. Login, manual Check receipts and the browser online event retry reconciliation. AES-GCM updates use revision compare-and-swap within IndexedDB transactions to prevent concurrent tabs overwriting balances/contacts. Only already-delivered, signed matching acknowledgements are applied; reconnecting never turns an unacknowledged transfer into success. Importing the same receipt repeatedly cannot debit twice. No incoming offer is auto-accepted.

**Cloud synchronization and automatic online delivery remain unavailable because no backend is configured.** The reconnect handler reconciles local imported receipts only; it does not contact a server, discover another phone, deliver offers or settle funds. Online Payment explicitly uses the same manual QR channel. There is no Bluetooth, NFC, background transport, authoritative global account directory, trusted balance server or double-spend prevention across cloned/restored/malicious device states.

## Android and iPhone

Android 8.0+ APK bundles static assets on a trusted local HTTPS origin. Only Internet and Camera permissions are declared; no SMS, microphone, contacts or broad storage permission. Camera is optional and starts only on user action. Native QR/public-receipt sharing uses an origin-restricted bridge, fixed cache filenames and a non-exported FileProvider with temporary read grants; the user chooses the destination. The picker accepts image QR codes or JSON receipt bundles according to the selected input. Private profiles/PINs/keys are never shared through this bridge.

On iPhone use Safari Share → Add to Home Screen, or reopen the existing installation online until Version 3.2.2 · Offline ready appears. Do not delete/clear data to update. The authenticated profile can then be unlocked offline using its PIN. WebKit/iPhone and Chromium/Android browser profiles in tests are desktop simulations, not physical-device certification. Real camera capture of screens/printed codes, actual Wi-Fi/mobile-data toggles, installed iPhone PWA cold launch, native sharing destinations and audible speech remain unverified without phones.

## Validation and deployment

`npm test` runs real crypto, protocol, PIN vault, QR decoding and cache checks. `npm ci`, `npx playwright install --with-deps chromium webkit`, `npm run test:browser` run registration/login/isolation, trusted-name resolution, PKR 100 signed QR transfers using actual displayed QR rasters, both cross-engine directions online/offline, receipt matching, failed/invalid/duplicate handling, full browser restart, offline PIN unlock and reconnect reconciliation. Test users are Adil (Android profile) and Usama (iPhone profile), with synthetic local-only numbers. No SMS is sent. Signing, decoding and encrypted storage are real; camera streams, browser profiles and network disconnection are simulated.

GitHub Pages deploys this existing repository. Android release publication requires the same commit's browser verification and seven emulator checks to pass, then validates signature/manifest/checksum before GitHub Releases. The existing Android signing identity is retained. No banking API or credentials are added. Vendored jsqr 1.4.0 (Apache-2.0) and qrcode-generator 1.4.4 (MIT) keep their license files.

Camera automation details: Chromium positive-camera coverage uses a synthetic canvas capture stream rendered through browser video. Headless WebKit canvas capture intermittently provides no frames, so its positive camera pipeline uses an explicitly injected video frame surface with the actual QR decoder/signature verification; it is not native camera capture. Both engines separately test no-frame timeout and real QR-image fallback. Physical iPhone camera capture is unverified.

## v3.1 payment flow and iPhone audio update

Scanning now fills the full recipient Account ID and resolved name automatically. Local registration-directory and previously checked contact records take precedence over arbitrary QR labels online and offline. No remote registered-account database exists; internet availability alone does not verify a new person. Unknown names stay explicitly self-declared until the user independently checks the account owner and saves the displayed details. This is local contact confirmation, not OTP or legal identity verification. No account details need to be copied/pasted.

There is no redundant account re-scan when selecting Online Payment. Select the payment mode before scanning; receiver details advance directly to amount/review. The additional payment QR transports the signed transaction, and the receipt QR transports the receiver acknowledgement. Removing these without another cross-platform delivery channel would produce undelivered payments or false success. The existing optical protocol, ledger schema, replay checks and PIN-encrypted account format are retained. Pending reservations cannot be cancelled unilaterally.

The web soundbox now starts a bundled non-silent PCM WAV through HTML media playback synchronously from the Test sound tap. It checks playback promises and actual playing/ended/error events; blocked/absent playback is reported rather than silently swallowing AudioContext resume errors. Notification sounds run only after a newly accepted receiver transfer or a newly verified sender receipt; duplicate receipt scans do not announce again. Mute/background/logout stop audio. Native Android TextToSpeech remains a separate path. Browsers cannot reliably detect the iPhone silent switch, Focus, hardware volume or selected speaker, and the app cannot override them. Physical iPhone/Android audible output remains unverified.

Audio policy references: https://webkit.org/blog/6784/new-video-policies-for-ios/ and https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay . Automated browser tests distinguish actual media-element progression with a headless audio sink from mocked speech/restriction events and physical speaker output. PKR 100 test transfers use Usama/iPhone and Adil/Android browser profiles in both directions online/offline.

## In-app updates (v3.2)

The Updates button is available before and after login. Android uses an origin-restricted native message listener to request only the fixed public release metadata URL over HTTPS on a worker thread; remote pages/scripts remain blocked in the WebView. Requests are correlated, timed out, and bounded to 16 KB. No wallet data is sent. The UI validates the release verification flag, exact versioned repository APK URL, checksum/size and a strictly newer semantic version before offering Update app. Same/older, malformed, unverified and offline responses do not offer a download. Android opens the APK URL through the browser and still requires its normal download/install confirmation. No silent installation, new install permission or new signing key is introduced.

Existing APKs must install this version once to acquire the button. Later APK releases can be discovered from inside this installation; opening the public website cannot replace old bundled APK code. Do not uninstall or clear app data. Web/iPhone installations check a network-only app-version.json and can request a normal service-worker update plus a user-triggered online reload. Saved encrypted accounts/history remain in IndexedDB; unsaved form state closes on reload.
